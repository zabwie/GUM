# E050 — Full-system profile of the 6.99 tok/s spec path (2026-11-10)

Baseline reproduced first, un-profiled: hybrid drafter (MTP+PLD), γ=16, agent trace, 64 gen
tokens, hot 8192 / cache 5600, `--expect-ids` PASS (mismatches=0):
**spec_summary: cycles=22, emitted=75, mean 3.409 tok/cycle, mean_cycle_s=0.4877, tok_per_s=6.990**,
acceptance 0.340. Raw: `results/e050-baseline-agent-g16-20261110.txt`.
Profile: `results/e050-spec-agent-g16.nsys-rep` (cuda+osrt, no sampling), sqlite analyzed
over the last 10.9 s (the 22 decode cycles).

## Headline: the pass is NOT copy-bound anymore — it is GEMV-bound

E047's "H2D-copy-bound at 13.6 GB/s" is superseded at the γ=16 hybrid config:

| quantity | value | share of 488 ms cycle |
|---|---|---|
| GPU busy (union of kernels+copies) | 98.1% of wall | — |
| **k_mat_q4 (GEMV, all items incl. MTP)** | 271 ms/cycle | **55%** |
| **k_delta_net_multi** | 116 ms/cycle (44 × 2.63 ms) | **24%** |
| other kernels (attn 6.4, quant_x 5.0, small) | ~17 ms/cycle | 3% |
| copy-only phases (copy stream exposed) | ~82 ms/cycle | 17% |
| true GPU idle | ~9 ms/cycle | 2% |

Copy stream: 222 ms/cycle busy, 139 GB moved, **25.5 GB/s effective — at the PCIe peak
(24.6-25.9, E037)**. Copies already hide under compute; lifting "copy throughput" buys
nothing on this path. The E047 13.6 GB/s "effective" number was cold-set-bytes/pass-time,
not copy-engine throughput.

## Bottleneck 1 — k_mat_q4 runs at 53 GB/s logical; NB=16 collapses it 5.4x

Microbench `benchmarks/microbench/e050-gemv-load-decomposition.cu` (11652×5120 tensor,
29.8 MB, VRAM-resident, sm_86):

| variant | ms | logical GB/s |
|---|---|---|
| NB=1 (current kernel) | 0.123 | **273.4** |
| NB=2 | 0.139 | 241.6 |
| NB=4 | 0.213 | 157.3 |
| NB=8 | 0.372 | 90.2 |
| **NB=16 (production config)** | 0.663 | **50.6** |
| v1 NB=16, xq in regs (bound below) | 0.409 | 82.1 |
| v2 NB=16, no loads at all (ALU floor) | 0.050 | 665.7 |
| v3 NB=16, xs/xsum in smem, xq regs | 0.289 | 116.0 |

**E034's "~275 GB/s dp4a" was an NB=1 measurement.** The real pipeline has always run at
~50 GB/s at NB=16; it was hidden behind copies until the E047 pipeline deepening exposed it.

Load-stream decomposition of the 0.633 ms (v0 − subtractive):
- weight loads (2 B scalars at 18 B lane stride): ~0.11 ms — tolerable (NB=1 proves 273 GB/s with the same pattern)
- **xq vector loads: ~0.25 ms** — every (lane, block) re-reads all 16 vector slices; ~1.9 GB of xq requests per 30 MB launch, L1 thrashed by the streaming weights
- **xs/xsum loads: ~0.22 ms** — scalar 4 B loads at v-stride nb·4 B = 32x sector over-fetch (this stream was previously unnoticed)
- ALU (20480 dp4a + fp32 chain): 0.05 ms

Rejected fixes (measured, don't retry blind): repacked [quanta-plane|scale-plane] layout
0.85x (scale loads got worse); smem tile re-loaded per row 0.15-0.5x (barrier/latency
bound); smem tile loaded once = 0.71 ms ≈ current (16 B/lane smem reads are inherently
half-rate, 8-way bank conflicts).

**Fix design (unimplemented):** block loads xq tile [16][2560] (40 KB) + fused xs/xsum tile
(10 KB) into smem ONCE per K-half; rows processed grid-stride against the tile; deterministic
per-half partial y (NO atomicAdd — keep bit-exact vs CPU reference); optionally repack weight
rows so lanes read uint32s coalesced. Ceiling: v3 (116 GB/s) with weight loads still ugly;
with both fixed, 200-300 GB/s plausible → GEMV 271 → ~70-110 ms/cycle (2.5-4x).

## Bottleneck 2 — k_delta_net_multi: ~0.3% of fp32 peak

44 calls/cycle × 2.63 ms. Kernel (real_decode.cu:481): one thread per (head h, state row j)
= 48×128 = 6144 threads (48 blocks on 28 SMs), each serially looping S=128 **four times per
position × 17 positions**, reading `row[i]` at lane-stride 512 B (32x sector over-fetch;
state [h][j][i] layout), half the 256-thread blocks idle (j≥S). 107 MFLOP/call → 40 GFLOP/s.

Fix: transpose state to [h][i][j] (lanes read consecutive i), split the S-loop across
warps with per-row smem reduction, 2D grid. Est. 116 → ~5-15 ms/cycle. Watch the
`h % ngroup` v-head→k-head mapping (ggml semantics, see memory note) and the E043
snapshot/rollback layout when touching state.

## Bottleneck 3 — copy chain becomes the next wall (after 1+2 land)

Copy chain = 222 ms/cycle = 5.42 GiB cold re-streamed ÷ 25.5 GB/s. As an equation:
**cycle ≈ max(compute_chain, cold_GiB/25.5 GB/s)**, tokens/cycle = 3.409 today.
After levers 1+2 (compute ~100-140 ms), the copy chain bounds the cycle at ~230-250 ms →
**~13-15 tok/s at TODAY's 34% acceptance**. Past that, the terms to attack are cold bytes
per pass (hot hit-rate sizing) and tokens per pass (drafter acceptance — ledger lever 2).
Zero-draft verify bound 20.4 tok/s (E047) is consistent with this.

Minor: k_attn_decode 6.4 ms/cycle (known O(context) serial, hd=128 half-idle — only matters
after 1+2); rollback snapshot/restore D2D 151 MB × 39 = 35.6 ms TOTAL (negligible — the E043
hybrid-state tax is already cheap); GPU idle 2%.

## Correctness notes

  fix must stay bit-exact: no atomicAdd in the reduction path.
- NB template note: g_batch must be set AFTER multi/speculate adjustments (E040 bug class);
  the smem fix changes the NB=16 path only.
